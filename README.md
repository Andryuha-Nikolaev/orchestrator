# Репозиторий агентов

Этот репозиторий нужен для хранения, редактирования и развития набора рабочих агентов, которые потом переиспользуются на разных проектах.

## Цель

- Держать в одном месте стабильные роли агентов и их поведение.
- Улучшать качество ответов и решений через итерации.
- Быстро переносить проверенных агентов в новые рабочие пространства.

## Структура

```text
agents/
	orchestrator.agent.md
	planner.agent.md
	coder.agent.md
	designer.agent.md
```

Кратко по ролям:

- `Orchestrator` — разбивает задачу на этапы и делегирует подагентам.
- `Planner` — проводит исследование и строит план реализации.
- `Coder` — пишет и меняет код по требованиям.
- `Designer` — отвечает за UI/UX-часть.

## Обязательный межагентный workflow

- `Planner` сначала задает уточняющие вопросы, если в задаче есть неопределенность.
- `Planner` всегда предлагает 2-3 варианта решения и явно выделяет приоритетный вариант с кратким обоснованием.
- `Orchestrator` показывает пользователю финальный план и ждет явный утвердительный ответ перед запуском исполнения.
- Если план не принят, `Orchestrator` собирает замечания, задает уточняющие вопросы и возвращает задачу `Planner` на перепланирование.
- Лимит итераций перепланирования не вводится.
- `Coder` и `Designer` используют Playwright MCP только для web/UI задач.
- Для non-web/UI задач в отчете обязательно указывается, что Playwright MCP неприменим.

### Подтверждение плана

- Явный утвердительный ответ может быть в свободной форме (например: "да", "согласен", "подтверждаю", "ок").
- Неоднозначные или смешанные ответы (например: "да, но...") считаются запросом на доработку, а не подтверждением.

### UX-ветка подтверждения

- Если клиент поддерживает action buttons, `Orchestrator` должен предлагать действия `Confirm` и `Revise`.
- Если action buttons недоступны, используется текстовый fallback с тем же смыслом.

## Что хранится в `.agent.md`

Каждый файл агента содержит:

- Frontmatter (имя, описание, модель, набор инструментов).
- Системные правила роли.
- Ограничения и обязательный workflow.

Рекомендуемый каркас:

```md
---
name: AgentName
description: One-line purpose
model: GPT-5.3-Codex (copilot)
tools: ['vscode', 'read', 'edit']
---

# Role

Краткое назначение.

## Workflow

Пошаговый рабочий процесс.

## Rules

Обязательные правила и ограничения.
```

## Процесс улучшения агентов

1. Зафиксируй проблему

- Что именно не сработало: пропуск требований, слабая декомпозиция, не тот тон, плохой план, лишние изменения.

2. Измени минимально

- Редактируй только нужный агент и только те правила, которые закрывают конкретный дефект.

3. Проверь на сценарии

- Прогони 2-3 типовых запроса: простой, средний, с конфликтами/краевым случаем.

4. Оцени регрессии

- Убедись, что улучшение не ломает другие сценарии и не делает агента слишком жестким.

5. Зафиксируй результат

- Запиши, что изменено и какой эффект ожидается.

## Принципы качества

- Конкретность: меньше абстракций, больше проверяемых инструкций.
- Проверяемость: правила должны вести к наблюдаемому результату.
- Ограниченность: избегай чрезмерно длинных и конфликтующих требований.
- Ролевая чистота: каждый агент делает свою часть работы.
- Переиспользуемость: инструкции не должны быть привязаны к одному проекту без необходимости.

## Как переиспользовать на новом проекте

1. Скопируй нужные файлы из `agents/` в новый workspace.
2. Проверь совместимость инструментов и модели в frontmatter.
3. Адаптируй только проектно-специфичные правила (пути, стек, внутренние конвенции).
4. Оставь базовые принципы неизменными, если они уже доказали эффективность.

## Когда создавать нового агента

Создавай нового агента, если одновременно выполняются условия:

- Появилась повторяющаяся отдельная роль.
- Эту роль нельзя чисто закрыть текущими четырьмя агентами.
- Есть понятные границы ответственности.

Иначе лучше расширить текущего агента точечными правилами.

## Чеклист перед коммитом

- Название и описание агента отражают реальную роль.
- Нет противоречащих друг другу правил.
- Workflow описан шагами, а не общими фразами.
- Ограничения явно сформулированы.
- Изменения проверены минимум на нескольких сценариях.

## Версионирование изменений

В сообщениях коммитов удобно использовать формат:

- `agents: clarify planner edge-case handling`
- `agents: tighten orchestrator phase conflict rules`
- `agents: refine coder coding principles`

Это упрощает поиск эволюции поведения каждого агента.
